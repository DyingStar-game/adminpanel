# 0024. Game services in the panel, social moderation first

- **Status:** Accepted (2026-10-08)
- **Date:** 2026-10-08
- **Deciders:** maintainer
- **Scope:** Project-wide (services), Social moderation (first service)
- **Builds on:** [ADR 0023](./0023-keycloak-authentication.md) (sign-in, one panel per
  environment, permissions, calling the services)

## Context

The panel manages persistence only. **Every game service will be managed by it** (maintainer,
2026-10-08): `social` first, then `economie`, `inventory`, `mission`, `market`. Each service has
its own OpenAPI in [`DyingStar-game/services`](https://github.com/DyingStar-game/services)
(`<service>/openapi.yaml`), checks Keycloak tokens itself, and is reached by the back team's
`svc-admin` account for its internal routes.

Facts this ADR relies on (checked 2026-10-08, GET only):

- **One panel per environment, one game server per environment** (ADR 0023). `SERVERS` (a list)
  and the `X-Server-Id` header are leftovers of a multi-server design.
- `social` moderation is `/api/admin/*`: 11 routes, the user's token, roles `moderator` <
  `admin` < `supervisor` checked by `social` (`social/src/routes/admin.routes.ts`):

  | Route | What | Minimum role |
  |---|---|---|
  | `GET /stats` | Community analytics (`CommunityStats`: players, corporations, reports, sanctions, activity last 24 h, most reported, lowest reputation) | `moderator` |
  | `GET /log?limit&offset` | Moderation audit log (`ModerationLogEntry`: actor, action, target, details) | `moderator` |
  | `GET /reports?status&escalation&targetPlayerId&limit&offset` | Report queue (`ReportView`, with reporter and target names) | `moderator` |
  | `GET /reports/{id}` | One report | `moderator` |
  | `PATCH /reports/{id}` | Status `reviewing` / `resolved` / `dismissed`, optional note | `moderator` |
  | `POST /reports/{id}/escalate` | Raise to `admin`, then `supervisor` | `moderator` |
  | `GET /players/{playerId}` | Player moderation sheet | `moderator` |
  | `POST /players/{playerId}/sanctions` | `warning`, `mute` (`moderator`); `suspension`, `ban` (`admin`) | `moderator` / `admin` |
  | `POST /players/{playerId}/reputation` | Adjust reputation | `admin` |
  | `GET /sanctions?playerId&active&limit&offset` | Sanctions | `moderator` |
  | `DELETE /sanctions/{id}` | Lift a sanction | `moderator` |

- Dev-local (minikube): `social` answers at `http://services.dyingstar.local/social/api/…`; it
  **rejects every token today** (no `OIDC_JWKS_URL`, the JWKS URL resolves to the pod itself),
  reported to the back team, fix expected 2026-10-08 evening. Its database is empty.
- The roles `admin` and `supervisor` exist in our local realms only.

## Options considered

How the panel describes a service's API:

1. **Hand-written Zod schemas** (as for persistence) — full control, but every service has
   dozens of schemas (`social`: 100+), copied by hand and drifting.
2. **Generated from the service's OpenAPI** — a pinned copy of `openapi.yaml` per service, Zod
   schemas and types generated by a reputable generator (`@hey-api/openapi-ts` with its Zod
   plugin; `openapi-typescript` gives types only, no runtime validation), a sync test against
   GitHub like the definitions' (`github-sync.test.ts`).

How the BFF exposes a service:

- **A. A transparent proxy** (`/api/social/*` → `social`) — little code, but the browser could
  reach any route the token allows, and nothing is validated on the way.
- **B. Curated routes** — the BFF declares the routes the panel uses, validates inputs and
  outputs with the generated schemas, and maps errors like persistence's.

## Decision

Option 2 and B, as a pattern repeated per service. `social` moderation is the first one.

### The per-service pattern

| Piece | Per service | `social` |
|---|---|---|
| Configuration | One URL per service in the panel's environment (`<SERVICE>_URL`); unset, the service is hidden, without error | `SOCIAL_URL` (minikube: `http://services.dyingstar.local:<port>/social`) |
| Contract | `packages/contracts/<service>/openapi.yaml` (pinned, with its source commit) + generated schemas, `make contracts-update`, a GitHub sync test | `social/openapi.yaml` from `develop` |
| BFF | `clients/<service>.ts` on a shared upstream client (timeouts, error mapping), routes `/api/<service>/…` declaring each the credential sent (user token or `svc-admin`) | `/api/social/…`, user token |
| Permissions | Its table in ADR 0023's matrix; for routes the service checks itself, permissions in `permissions.ts` **mirror** its roles (UI only) | `social.moderate` (`moderator`+), `social.sanctionSevere` and `social.reputation` (`admin`+) |
| Tests | An MSW mock in `packages/testing`, from fixtures typed by the generated types | `createSocialMock` |
| SPA | A module in a registry (sidebar section, pages, labels in `en` / `fr`), shown when configured and allowed | "Moderation" section |
| Local dev | Minikube mode (`make up K8S=1`) | as is |

When a service is unreachable or refuses, its pages say so; the rest of the panel keeps working.

### Configuration: from `SERVERS` to the panel's services

In the same step, `SERVERS` and `X-Server-Id` give way to the panel's own settings:
`GAME_SERVER_NAME` (shown in the top bar), `PERSISTENCE_URL`, `SOCIAL_URL`, … The browser never
sees these URLs (ADR 0011). The persistence routes stop requiring `X-Server-Id`.

### Social in the panel: what is wanted, in three steps

Asked by the maintainer (2026-10-08): **administer the players** (see their profile, ban…) and
**see the organisations** (corporations and political entities). The sidebar's
"Administration" section holds **Players**, **Moderation** and **Organisations**, all opened by
`social.moderate` (`moderator` and above).

1. **Reading** — done first: moderation overview (stats, log), report queue and a report,
   sanctions, the player moderation sheet (`/api/admin/players/{id}`); then **Players**: search
   by name, players or NPCs (`GET /api/profiles?search&entityType`, a player route called with
   the moderator's token: `social` has no admin listing), each opening the sheet.
2. **Organisations, reading**: corporations (`GET /api/corporations…`: list and search, page,
   members and ranks, subsidiaries, activity) and political entities (`GET /api/politics…`:
   list by type, page, members and offices, children, activity). Player routes too, any
   signed-in player may read them: the panel's permission is what restricts them. Creating,
   editing or disbanding an organisation goes through `/api/internal/*` (`svc-admin`) and waits
   for ADR 0023's management table.
3. **Acting on players**: sanction (warning, mute; suspension and ban for `admin`+), lift a
   sanction, adjust reputation (`admin`+); then the report actions (status with a note,
   escalate). Each confirmed, like persistence writes, and refreshed after.

Each action button follows the user's moderation role (hidden when `social` would refuse);
`social` stays the authority and its 403 is shown as such. Player routes apply sanctions to the
**caller**: a moderator who is suspended in game is refused there too (`403 SANCTIONED`), and
they return public profile fields only (the sheet holds the moderation detail).

### Signing in with a moderation role

With the moderation module built, `moderator`, `admin` and `supervisor` open the panel again
(they hold `social.*` permissions), seeing moderation only; persistence still needs a
`persistence:*` role (ADR 0023).

### Update (2026-10-08): report actions by escalation level, staff known to `social`

Decided by the maintainer after step 3's report actions were tried on minikube:

- **A report is handled at its escalation level.** Changing its status or escalating it needs a
  moderation role at least equal to its level: `moderator` for a `moderator` report, `admin`
  for an `admin` one, `supervisor` for a `supervisor` one. `social`'s README describes
  escalation as going to "instances supérieures", and `social` opens its own reports at the
  `admin` level, but its code lets any `moderator` act at any level: the panel enforces the
  rule (permissions `social.reportsAdmin`, `social.reportsSupervisor`; the BFF reads the
  report's level before forwarding, the SPA shows the actions only to those who may), and the
  back team is asked to enforce it in `social`. The panel stays allowed to grant less than
  `social` (ADR 0023).
- **A report is claimed before anything else.** An open report offers one action, "Claim"
  (status `reviewing`); only then may it be confirmed (`resolved`), dismissed or escalated.
  Escalating sends it back to `open`, to be claimed at its new level. `social` accepts any
  order: the panel enforces this one (`reportActions` in `packages/schemas`, checked by the BFF
  before forwarding, followed by the SPA).
- **Staff accounts are registered in `social` at sign-in.** `social` requires the author of a
  reputation change to have a profile (`reputation_events.actor_id`), which it only creates on
  an account's first `GET /api/me`: a moderator who never played could not accept or dismiss a
  report, nor adjust reputation. After a sign-in holding `social.moderate`, the BFF calls
  `GET /api/me` with the user's token, best effort (a failure is logged, the sign-in goes on).
  Staff accounts thus get a player profile in `social` (searchable, with a reputation): they are
  players too (realm role `player`). Asked of the back team: accept an author without a profile.

## Consequences

- One more workspace package (`packages/contracts`) and a code generator in the toolchain; the
  generated files are committed, so a build never depends on GitHub.
- Adding a service becomes a checklist (contract, client, routes, permissions, mock, module),
  recorded in `CLAUDE.md` once the first one is done.
- Removing `SERVERS` changes `.env.sample`, `.env.local` files and deployments: a migration note
  is needed.
- Moderation data is personal data of players (names, reports, sanctions): the panel shows it to
  moderators only and logs nothing of it.
